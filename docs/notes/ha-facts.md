# HA developer fact sheet for goto_connect rewrite (researched 2026-10-17)

NOTE: developers.home-assistant.io now 301-redirects to contributors.home-assistant.io (old /docs/... paths -> /core/...). Source of HA code facts = `dev` branch on raw.githubusercontent.com. Confidence tags: [H] read in primary source, [M] inferred/secondary, [L] not verified.

## 1. Entity-based notify
Docs: https://contributors.home-assistant.io/core/entities/notify/ ; blog https://contributors.home-assistant.io/blog/2024/04/10/new-notify-entity-platform/ ; code https://github.com/home-assistant/core/blob/dev/homeassistant/components/notify/
- [H] Subclass `NotifyEntity` (`homeassistant.components.notify`). Implement `async def async_send_message(self, message: str, title: str | None = None) -> None` (or sync `send_message`). Optional `NotifyEntityDescription`. `_attr_supported_features = NotifyEntityFeature.TITLE` only if title supported (otherwise title not passed through).
- [H] Platform file `notify.py` with `async_setup_entry(hass, entry, async_add_entities)`; add `Platform.NOTIFY` to forwarded platforms.
- [H] State = ISO timestamp of last message sent (base class sets it; restored). Base records messages sent via `notify.send_message`; if you send by another path call `self._async_record_notification()`.
- [H] Targeting: service `notify.send_message` with target = entity of domain `notify`; fields `message` (required), `title` (optional, only for entities with TITLE feature) (notify/services.yaml). NO recipient/target parameter exists. Blog: "takes no targets because you can target multiple notify entities directly"; recipient/contact-registry support was "ongoing discussion" (2024). => pattern is one entity per destination/sender. Per-call recipient (SMS to arbitrary number) is NOT expressible via notify.send_message; keep that in a custom service (see 4).
- [H] Legacy: `notify/legacy.py` in dev STILL loads platforms defining `async_get_service` or `get_service` (`BaseNotificationService`, `.targets` -> registers `notify.<prefix>_<target>` services). No deprecation warning/removal date in the loader. `repairs.py::migrate_notify_issue` exists but is called by individual core integrations (is_fixable, breaks_in_ha_version caller-supplied), not by the loader.
- [M] Direction: "Entity platform implementations will replace the legacy notify action in time"; core integrations are migrating in phases (Telegram legacy removal planned then postponed, core issue #164855, closed not planned Jun 2026). Telegram case shows the `alert` integration still only works with legacy services.
- [M] BOTH legacy shim and entities simultaneously: technically possible (different mechanism: legacy loaded via `notify:` YAML/`discovery`-style `async_load_platform`/ legacy platform setup; entities via config-entry platform forward). A custom integration can do both; legacy `get_service` for a config-entry integration needs `discovery.async_load_platform` from `async_setup_entry`/`async_setup` [L, pattern not re-verified, the current goto_sms code already does something]. Risk: legacy path is EOL-trajectory; a core submission must use entities only.
- Version floor: notify entity platform landed 2024.4/2024.5 [L, blog dated 2024-04-10; exact release unconfirmed]; `title` support added ~2024.5 (blog 2024-05-03 https://developers.home-assistant.io/blog/2024/05/03/notify-title).

## 2. Application Credentials + OAuth2
Docs: https://contributors.home-assistant.io/core/integrations/oauth2/ ; code https://github.com/home-assistant/core/blob/dev/homeassistant/helpers/config_entry_oauth2_flow.py
- [H] manifest.json: `"dependencies": ["application_credentials"]`, `"config_flow": true`. (Also `"after_dependencies"`/`my` not needed; `my` comes with default_config.)
- [H] `application_credentials.py`: `async def async_get_authorization_server(hass) -> AuthorizationServer` returning `AuthorizationServer(authorize_url=..., token_url=...)`. Optional `async_get_auth_implementation(hass, auth_domain, credential)` (e.g. `LocalOAuth2ImplementationWithPkce`, verifier length 43-128) for PKCE or custom token handling; subclass `AuthImplementation` for non-standard token exchange (e.g. Basic-auth header client creds). Optional `async_get_description_placeholders(hass)` (console_url etc.). `strings.json` needs `application_credentials.description`. New integrations must NOT accept YAML client creds.
- [H] Config flow: `class OAuth2FlowHandler(config_entry_oauth2_flow.AbstractOAuth2FlowHandler, domain=DOMAIN)`; override `logger` property, `extra_authorize_data` (scopes), `async_oauth_create_entry(data)` (set unique_id, title; handle reauth). Scaffold: `python3 -m script.scaffold config_flow_oauth2`.
- [H] Reauth: `async_step_reauth(entry_data)` -> `async_step_reauth_confirm` (shows form, then `async_step_user`). In `async_oauth_create_entry`: if `self.source == SOURCE_REAUTH`: `self._abort_if_unique_id_mismatch()`; `return self.async_update_reload_and_abort(self._get_reauth_entry(), data_updates=data)`; else `_abort_if_unique_id_configured()` + `async_create_entry`.
- [H] Runtime: `implementation = await config_entry_oauth2_flow.async_get_config_entry_implementation(hass, entry)`; `session = config_entry_oauth2_flow.OAuth2Session(hass, entry, implementation)`; before each request `await session.async_ensure_token_valid()` then `session.token["access_token"]`. Refreshed tokens are persisted to the entry automatically. Library should take a token-provider callback (don't refresh itself).
- [H] Error mapping (recent): `OAuth2TokenRequestReauthError` (HTTP 400-499 except 429) -> reauth (ConfigEntryAuthFailed); `OAuth2TokenRequestTransientError` (429/5xx) and `OAuth2TokenRequestConnectionError` -> ConfigEntryNotReady. `async_get_config_entry_implementation` raises `ImplementationUnavailableError` (NotReady) / `UnknownImplementationError` (AuthFailed). Let them propagate; no strings needed.
- [H] Redirect: `async_get_redirect_uri(hass)` returns `https://my.home-assistant.io/redirect/oauth` whenever the `my` component is loaded (default_config); otherwise `<HA-Frontend-Base>/auth/external/callback`. Applies equally to custom integrations: register `https://my.home-assistant.io/redirect/oauth` as the redirect URI in the GoTo OAuth client. (Users with a custom setup w/o `my` must register their own URL.)
- Version: application_credentials platform merged May 2022 => HA 2022.6 [M, https://github.com/home-assistant/core/pull/71880]. Error classes/`async_update_reload_and_abort`/`_get_reauth_entry` are newer (2024.11+/2025.x) [L exact]; pick floor accordingly.

## 3. Domain rename
- [H] No supported API to change a config entry's domain. `ConfigEntry.domain` is immutable; `async_update_entry` has no domain param; config-entries doc (https://contributors.home-assistant.io/core/integrations/config-entries/) does not mention domain change.
- [M] Accepted UX: ship new integration; users add it fresh; old one removed. Real precedents found: iocare (delete + re-add, https://github.com/bedgar/home-assistant-iocare); securitas->verisure_owa PLAN (https://raw.githubusercontent.com/guerrerotook/securitas-direct-new-api/main/docs/FUTURE_MIGRATION_PLAN.md): legacy domain detects new install, migrates data, removes itself, Repairs issue tells user to remove old repo from HACS. Mechanics available to build this yourself: in new domain's config flow add `async_step_import`/or a first step that scans `hass.config_entries.async_entries("goto_sms")` and copies tokens/data (`entry.data`) into the new entry (source import/user), then `ir.async_create_issue(hass, DOMAIN, "migrated_from_goto_sms", is_fixable=False, severity=WARNING, translation_key=...)` and optionally `hass.config_entries.async_remove(old_entry.entry_id)`. Both domains can coexist in custom_components during a transition release (two directories, one HACS repo is ONLY ONE integration dir allowed though: HACS manages one `custom_components/<x>` per repo; a second dir is ignored => transition needs the old domain to be updated in-place or a separate repo).
- Important HACS constraint [H]: https://www.hacs.xyz/docs/publish/integration/ "Only one integration per repository... only the first is managed."
- Alternative (keep domain `goto_sms` for HACS phase, migrate later at core submission): see #9. Core submission with a different domain than the HACS one would need the same fresh-add UX anyway, so renaming at HACS phase vs core phase costs users the same once.

## 4. Custom services
Docs: https://contributors.home-assistant.io/core/integrations/actions/ ; rule https://contributors.home-assistant.io/core/integration-quality-scale/rules/action-setup (md in developers repo)
- [H] Register in `async_setup(hass, config)` (NOT `async_setup_entry`) so actions exist/validate even if no entry loaded (Bronze rule `action-setup`). Requires `CONFIG_SCHEMA = cv.config_entry_only_config_schema(DOMAIN)`. In handler, look up entry with `service.async_get_config_entry(hass, DOMAIN, call.data["config_entry_id"])` (or pass target at entry/device level) and raise `ServiceValidationError` (user error) / `HomeAssistantError` with translated messages.
- [H] `hass.services.async_register(DOMAIN, "call_tts", handler, schema=..., supports_response=SupportsResponse.OPTIONAL)`; handler returns JSON-serializable dict; caller uses `response_variable` in scripts or `?return_response`. NONE (default)/OPTIONAL/ONLY. OPTIONAL is the right choice for returning call outcome. `services.yaml` with name-without-domain keys, fields with selectors, `target`/`filter`/`sections`; names/descriptions in `strings.json` (`services` section) and `icons.json`.
- [H] Core-submission scope: https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/docs/core/integration/contributing_to_core.md says the FIRST PR should omit "custom service actions" => voice-call service belongs in a follow-up PR.
- Version: service responses 2023.7 [H, https://www.home-assistant.io/blog/2023/07/05/release-20237/].

## 5. TTS rendering server-side
Code: https://github.com/home-assistant/core/blob/dev/homeassistant/components/tts/__init__.py
- [H] `tts.async_get_media_source_audio(hass, media_source_id) -> tuple[str, bytes]` (extension, data) - for `media-source://tts/...` ids.
- [H] Preferred for direct use: `stream = tts.async_create_stream(hass, engine, language=None, options=None)` (returns `ResultStream`); `stream.async_set_message(text)`; `async for chunk in stream.async_stream_result()`; `stream.extension`, `stream.content_type`. `tts.async_resolve_engine(hass, engine)`, `tts.async_default_engine(hass)`. Manager: `SpeechManager.async_create_result_stream(...)`.
- [H] Format control via options: `preferred_format`, `preferred_sample_rate`, `preferred_sample_channels`, `preferred_sample_bytes`, `preferred_bitrate`. If the engine can't produce it natively, tts core transcodes with ffmpeg automatically. Default ext is mp3. So request `{"preferred_format":"wav","preferred_sample_rate":8000,"preferred_sample_channels":1,"preferred_sample_bytes":2}` and no own ffmpeg needed. (Our SIP codec is PCMA/G.711A, 8 kHz: ask for 8k mono 16-bit WAV, then lin->alaw in lib via audioop-lts/own table.) [M: whether engines with unsupported rates are resampled - doc says yes for non-native, "Conversion is skipped when output already matches"].
- [H] Entities implement `async_get_tts_audio(message, language, options) -> (ext, bytes)`; `tts` dependency in manifest (`"dependencies": ["tts"]`, or after_dependencies).
- [H] core `voip` (assist_satellite.py): uses `tts_options` = WAV 16000 Hz 1ch 2 bytes; `tts.async_get_stream(hass, token)` -> `ResultStream`; `await stream.async_stream_result()`; asserts `extension == "wav"`; parses with `wave`; reads PCM frames and sends via RTP in executor (`voip_utils`). Announce flow `outgoing_call(...)`. No ffmpeg direct use. voip manifest: deps assist_pipeline, assist_satellite, intent, network; requirement voip-utils; quality_scale internal.
- [H] ffmpeg component (https://github.com/home-assistant/core/blob/dev/homeassistant/components/ffmpeg/__init__.py): `get_ffmpeg_manager(hass).binary`, `async_get_image`, no transcode helper. Use tts preferred_* options instead, or run `manager.binary` yourself.

## 6. HACS default store
Docs: https://www.hacs.xyz/docs/publish/include/ , /docs/publish/integration/ , /docs/publish/start/
- [H] Public GitHub repo, not archived, description, issues enabled, topics. At least one FULL GitHub release (not just tag). OSI-recognizable license (GitHub-detectable; NOASSERTION/non-commercial fail).
- [H] Layout: exactly one `custom_components/<domain>/`; manifest needs `domain, documentation, issue_tracker, codeowners, name, version`. hacs.json at repo root: `name` (required); optional `homeassistant` (min HA version, append `b0` for betas), `hacs` (min HACS), `country`, `content_in_root`, `zip_release`+`filename`, `hide_default_branch`, `persistent_directory`. Without releases HACS tracks default branch; with releases shows latest 5 + default.
- [H] Brands: "needs a brand directory with at least an icon.png, OR its domain exists in home-assistant/brands" (include page). I.e. `custom_components/<domain>/brand/icon.png` now satisfies it (HA 2026.3+). Domain must not conflict with core domain incl. next release.
- [H] CI: HACS Action and hassfest must pass with no ignores. README: no stated requirement for integrations (but recommended).
- [H] PR: only owner/major contributor; fork hacs/default, branch from `master`, not from an org account; add repo alphabetically to `integration` file; fill whole template; minor issues -> draft, major -> closed; backlog "can take months". Custom integrations that test/override core integrations rejected.
- Changed recently: brands now optional-in-repo via local `brand/` dir (2026.3); backlog note.

## 7. home-assistant/brands
Repo: https://github.com/home-assistant/brands ; blog https://contributors.home-assistant.io/blog/2026/02/24/brands-proxy-api ; docs https://contributors.home-assistant.io/core/integration/brand_images
- [H] `custom_integrations/` is now a LEGACY folder: since HA 2026.3.0 custom integrations ship images in `custom_components/<domain>/brand/` (icon.png, dark_icon.png, logo.png, dark_logo.png, plus @2x of each). Local files take priority over CDN; served via `/api/brands/integration/{domain}/{image}`. No central PR needed. `core_integrations/` is for core ones (submit brands PR when contributing to core; remove the local brand dir then).
- [H] Specs: PNG, transparent preferred, trimmed. icon 1:1 256x256 (512x512 @2x). logo landscape, shortest side 128-256 (256-512 @2x). dark_ variants optional (fall back to non-dark). Must not use HA-branded imagery. Quality rule `brands` is Bronze.
- Gotcha [M]: HA < 2026.3 will not show the local brand images (falls back to CDN/blank); brands-repo PR to `custom_integrations/goto_connect/` may still be wanted for older HA users, but README calls the folder legacy (may stop accepting) [L].

## 8. Core submission
Docs: https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/docs/core/integration/contributing_to_core.md ; rules https://github.com/home-assistant/core/blob/dev/script/hassfest/quality_scale.py ; https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/docs/core/integration-quality-scale/rules/
- [H] New integrations must reach Bronze (hassfest error "New integrations are required to at least reach the Bronze tier"); `quality_scale.yaml` with each rule done/exempt. Don't aim higher initially.
- [H] Bronze rules: action-setup, appropriate-polling, brands, common-modules, config-flow, config-flow-test-coverage, dependency-transparency, docs-actions, docs-conditions, docs-high-level-description, docs-installation-instructions, docs-removal-instructions, docs-triggers, entity-event-setup, entity-unique-id, has-entity-name, runtime-data, test-before-configure, test-before-setup, unique-config-entry.
- Silver: action-exceptions, config-entry-unloading, docs-configuration-parameters, docs-installation-parameters, entity-unavailable, integration-owner, log-when-unavailable, parallel-updates, reauthentication-flow, test-coverage (>95% all modules).
- Gold: devices, diagnostics, discovery, discovery-update-info, docs-data-update, docs-examples, docs-known-limitations, docs-supported-devices, docs-supported-functions, docs-troubleshooting, docs-use-cases, dynamic-devices, entity-category, entity-device-class, entity-disabled-by-default, entity-translations, exception-translations, icon-translations, reconfiguration-flow, repair-issues, stale-devices.
- Platinum: async-dependency, inject-websession, strict-typing.
- [H] Staged PR: first PR = ONE platform; omit diagnostics, custom service actions, reauth/reconfigure flows, dynamic/stale devices. (Note: reauth is Silver rule, so can follow later; but OAuth integrations still need to work.) Large code dumps may be closed. PR description: explain product + link to library repo.
- [H] Library: all comms in external PyPI lib; OSI license, built/published from public CI, each version matches a tag in open repo (dependency-transparency). (Another page says sdist required: [M], older dev checklist.) Eligibility: product must be purchasable/established.
- [H] Tests: config flow 100% coverage incl. all error paths, unique-id assert, duplicate abort (Bronze `config-flow-test-coverage`); >95% module coverage for Silver.
- [L] Review queue length: not measurable from docs; known to be slow (months). No stated gate beyond Bronze/hassfest/CI.
- [M] OAuth: `application_credentials` requires every OAuth integration to support it; reauth (Silver) typically still expected for OAuth.

## 9. Config entry version/migration
Docs: https://contributors.home-assistant.io/core/integrations/config-entries/
- [H] `VERSION` (major) and `MINOR_VERSION` on the ConfigFlow class (default 1). Minor bump = backwards compatible; major = breaking (older HA cannot set up). `async def async_migrate_entry(hass, entry) -> bool` in `__init__.py`, called before setup when stored major < current or minors differ. Use `hass.config_entries.async_update_entry(entry, data=new, version=2, minor_version=1)`. Check versions stepwise; if entry.version > ours (downgrade) return False. False/unexpected exception -> `MIGRATION_ERROR`; `ConfigEntryNotReady` retries.
- Alt plan (keep domain `goto_sms` in HACS phase): bump VERSION to 2 and migrate stored token/data shape in `async_migrate_entry`; then rename domain only at core submission (fresh add). Cheapest for existing users now, but defers the domain break.
- [H] No mechanism changes domain.

## 10. Minimum HA version strategy
- [H] hacs.json `homeassistant` key = min HA version HACS enforces (HACS refuses/warns install). manifest.json has no min-HA key for custom integrations (core only uses `version` for custom; HA does not enforce min). So set floor in hacs.json only.
- Introduced: service responses 2023.7 [H]; application_credentials 2022.6 [M]; NotifyEntity 2024.4-2024.5 [L, blog 2024-04-10]; NotifyEntity title 2024.5 [L]; custom brand/ dir 2026.3 [H] (only cosmetic); `async_update_reload_and_abort` + `_get_reauth_entry` + `OAuth2TokenRequest*Error` exceptions: 2024.11-2025.x [L].
- Suggested floor: 2025.1 if using `entry.runtime_data`, `_get_reauth_entry`; raise to whatever release added `OAuth2TokenRequest*Error` if you rely on it [L] - verify with a hassfest/`git log` check before pinning. 2024.11+ is safe for all except the error classes.
